# Setup Digger

現状を調べ、必要な選択を一つずつ確認し、使える取得環境と設定を残す。`digger` と同じ配布先に導入する。[設定の契約](../digger/references/configuration.md)を先に読む。見つからなければ `digger` の配布漏れとして報告する。

## 1. 現状を調べる

- 既存の利用設定と、このマシンの環境記録を読む。設定のある項目は引き継ぎ、今回の変更対象だけを聞く。
- OS・CPU、既存のパッケージ管理方法、利用可能な Web 検索・取得機能を確認する。既存ツールを優先し、すべての機能を前提としてインストールしない。
- Obsidian を利用する場合は `obsidian-vault` を読み、登録済み Vault と保存規約を確認する。スキルがなければ Obsidian 対応に必要なものとして提示する。
- 選択済み機能があれば [依存ツールの確認と導入](references/dependencies.md)で存在・言語・モデル・認証参照を確認する。認証情報の値は表示しない。

分かったことと不足を短く示す。初回は以下を順に聞き、回答から決まる項目を重ねて質問しない。

## 2. 保存先を選ぶ

Obsidian の Vault 内、または通常のディレクトリを選んでもらう。Obsidian を希望している場合は登録済み Vault の `digger-research/` を提案する。新しい最上位カテゴリになる場合はその配置も選択に含める。通常ディレクトリは既存の調査置き場を優先し、なければ `~/research` を提案する。

次に、大きな原本も同じ場所に置くか、別の原本ルートに置くかを決める。既定案は PDF を保持、音声・動画は抽出に使う一時コピーのみ。抽出テキスト・メタデータ・探索記録は常に調査先に残す。

Vault の実パスと選択した相対パスを確認する。別ルートも含め、実際に使う場所をユーザーへ示す。保存先変更時は今後の調査の設定を変更し、過去資料の移動は別の依頼として扱う。

## 3. 扱う資料と文字起こしを選ぶ

Web、PDF、画像PDFのOCR、動画字幕、音声からの文字起こしのうち必要な機能を選んでもらう。最初の提案は Web・PDF・動画字幕。資料の主な言語を確認する。

論文の引用索引を使う場合はOpenAlex、継続調査を希望する場合はRSS/Atomの確認も選択機能へ含める。実行環境の通信規約とサービスの利用条件を確認して、使える取得経路を環境記録に残す。

音声からの文字起こしを使う場合だけ、既存環境を踏まえてローカル方式と外部サービス方式を示す。実装・モデル・言語・必要容量を確認し、サービスなら送信先・費用・認証方法も説明して選ぶ。既存字幕の取得だけなら音声認識モデルは不要。

## 4. Wikiへの反映を選ぶ

調査前の既存知識の確認には、qmdが使えれば `vault-rag` の手順を利用する。対象collectionと選択したVaultの対応、索引の鮮度を確認して設定へ記録する。未導入なら索引・ファイル検索で代用でき、qmdを必須にはしない。Jevはこの版では導入・呼び出しを行わない。

既定案は `manual`：調査資料を保存して完了し、Wiki 更新は別途呼び出す。

調査後の Wiki 更新を希望する場合は、利用できる Wiki スキルを読み、対象 Vault、入力形式、更新範囲、確認手順を調べて説明する。現在の `wiki-update` は今回の資料に加えて未処理台帳なども処理するため、その通常の更新範囲を含めて選択された場合に `after-research` を設定する。設定した保存先で連携できない場合は `manual` のまま不足条件を伝える。

## 5. 導入内容を提示して適用する

Pythonは標準ライブラリだけで動くため、既存のPython 3.10以上を使う。解決先とバージョンを確認して実行経路を記録し、uvや仮想環境を新設しない。既存環境がmise管理なら `mise exec --` を使う。不足している場合だけ既存の管理方法でPythonを導入する。

APIキーが必要な選択機能では、保存方式（envchainまたは環境変数）、namespace、環境変数名を確認する。既存のnamespaceを勝手に変更しない。キー本体を会話や設定ファイルへ書かず、設定には認証参照だけを残す。envchainが使えるかと、対象プロセスで値を表示せずキーを利用できるかを確認する。サービスへの送信先・資料の範囲・費用を合わせて記録する。

選択内容をまとめ、利用設定の完成形と、不足ツール・言語データ・モデルのインストール先および実行予定のコマンドを示す。環境への変更内容をユーザーが確認できる形にし、承認済みの項目は聞き直さない。未承認のインストールだけ承認を得てから実行する。

[依存ツールの確認と導入](references/dependencies.md)に従って必要なものを導入する。既存のパッケージ管理方式を使い、未使用の機能のために環境を増やさない。選択機能ごとに実際の取得・変換を確認する。

## 6. 設定を書いて検証する

選択された利用設定を `config.json` に保存し、実測した確認結果を `environment.md` に書く。既存設定の変更は差分を確認してから行い、破損・未知の設定を既定値で上書きしない。

- 設定を読み直し、機能と言語・文字起こし・Wiki連携の整合を確認する。
- 調査先と別の原本ルートについて、選択されたディレクトリ内に小さな一時ファイルを書いて読み戻し、その一時ファイルだけ除去して保存可否を確認する。
- Obsidian は登録情報から再解決し、選択した Vault と一致することを確認する。
- 各機能を `ready` / `unverified` / `blocked` で記録する。失敗した機能を利用可能と報告せず、利用設定に残した希望と区別する。

すべての選択機能が `ready` ならセットアップ完了。それ以外は部分完了として、使える機能と残る条件を示す。設定・環境記録のパスと、`$digger 調べたい話題` の呼び出し例を返す。設定は直接編集でき、再セットアップでは変更した項目だけを再確認できることを伝える。
