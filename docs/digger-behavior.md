# digger の振る舞いとセットアップ

更新日：2026-10-21

`digger` は、未知の分野について引用・リンク・著者をたどり、原典と読むべき箇所を集めるスキルです。[imozuru](https://github.com/MaryCache/imozuru) の調査手順を土台に、保存先の選択、取得環境のセットアップ、Obsidian への保存を組み合わせます。

調査資料と探索経過を残し、原文、抜き書き、訳、AIの判断を区別します。調べ始めの段階で要約に結論を固定せず、ユーザーが原典を読んで判断できる形を目指します。

この文書は利用時の振る舞いを確認するための設計書です。Jevによる不足判定と引用確認は任意機能として実装しています。有効化と送信範囲の設定後、diggerの手順内で呼び出します。末尾に現在の実装との差分を記載しています。

## 1. 二つのスキルの役割

| スキル | 呼び出す場面 | 完了すると得られるもの |
|---|---|---|
| `setup-digger` | 初回利用、保存先変更、別マシンへの移行、取得環境の修復 | 利用設定と、このマシンで使える機能の確認結果 |
| `digger` | 未知の分野の調査、元になった資料の収集、以前の調査の続き | 原典、出典位置付きの抜き書き、探索地図、探索ログ |

呼び出しの例：

```text
$setup-digger
$digger 音声合成の低遅延ストリーミングについて調べたい
```

単一の事実確認や手元のファイル検索は、通常の検索で扱います。保存した資料の要約や解説、Wiki への統合は、原典の収集と分けて扱います。

## 2. 初回セットアップ

`setup-digger` は既存設定と実行環境を調べ、分かったことと不足を示します。選択が必要な項目だけを順に聞き、既存の回答から決まることは引き継ぎます。Matt Pocock さんのセットアップスキルと同様に、対話で選択し、適用内容を確認してから設定を保存する方式です。

### 保存先と原本の保持

調査資料の保存先は、Obsidian の Vault 内か、通常のディレクトリから選びます。Obsidian を希望する場合は登録済みの Vault を確認し、その中の `digger-research/` を候補にします。これは digger が管理する調査資料の置き場で、通常の手書きノートと区別します。既存の置き場を指定することもできます。

PDF・音声・動画の原本を、調査ノートと同じ場所に置くか、別の原本ルートに置くかも選べます。初期提案は PDF を保持し、音声・動画は文字起こしに使う一時コピーだけを取得する形です。ユーザーが渡した原本は削除しません。

保存先は、設定時に実際のパスを示します。再セットアップで保存先を変更した場合は、以後の調査に適用します。過去の資料の移動は別の作業です。

### 取得・変換する資料

使いたい機能と、資料の主な言語を選びます。最初の提案は Web・PDF・動画字幕です。

| 機能 | 処理 | 確認するものの例 |
|---|---|---|
| Web | 検索し、ページ本文を取得する | 検索機能、Web取得機能または `ax` |
| PDF | 原本を取得し、文字層から本文を抽出する | PDF取得機能、Poppler |
| 画像PDFのOCR | ページ画像から文字を読み取る | ページ画像化、OCR実装、対象言語データ |
| 動画字幕 | 公開されている字幕を取得する | `yt-dlp` 等、対象言語の字幕 |
| 音声の文字起こし | 音声を原言語のテキストに変換する | ローカル実装または外部サービス、モデル、必要に応じて FFmpeg |

既存字幕の取得と、音声からの文字起こしは別の機能です。字幕だけを使う場合は音声認識モデルを導入しません。

音声認識を使う場合は、既存環境を踏まえてローカル処理と外部サービスを比較します。モデル・言語・必要容量を決め、外部サービスでは送信先・費用・認証方法も確認します。字幕が取得できなかったことを理由に、未選択のサービスへ音声を送ることはありません。

### 認証情報の取り出し方

APIキーが必要な機能では、キーを管理する方法、namespace、環境変数名などの参照情報を聞きます。キー本体を会話や設定ファイルへ貼り付ける必要はありません。

Jev用のenvchain参照は、専用変数名 `DIGGER_TYPESAFE_API_KEY` とnamespace `digger` を提案します。既存の保存先が指定されていれば、その参照を使います。

```json
{
  "credentials": {
    "typesafe": {
      "method": "envchain",
      "namespace": "digger",
      "variable": "DIGGER_TYPESAFE_API_KEY"
    }
  }
}
```

キー本体は envchain 側で管理します。digger は記録した方法で必要なプロセスへ渡し、値を表示せず利用可否を確認します。認証設定を登録することと、そのサービスへ資料を送ることは別です。送信する資料の範囲は、機能を有効にするときに決めます。

登録コマンドは `envchain --set digger DIGGER_TYPESAFE_API_KEY` です。`jev.py` が指定変数からAPIキーを取得し、APIへ明示的に渡します。SDKは不要で、キーの登録だけでは連携を有効にしません。

### 不足ツールの導入と動作確認

セットアップは、選んだ機能に必要なツールだけを調べます。既存のパッケージ管理方法を使い、不足ツール・言語データ・モデルの導入先とコマンドを示して、確認された内容をインストールします。

完了判定には、短い公開サンプルまたは合成資料での取得・変換を使います。コマンドが存在しても、日本語OCRの言語データがなければ日本語OCRは利用可能としません。

### Pythonの選択

`report.py` は Python 3.10以上の標準ライブラリだけで動き、追加のPythonパッケージは不要です。既存のPythonを使い、diggerのためにuvや仮想環境は導入しません。

セットアップで使用するPythonの解決先とバージョンを調べ、スクリプトを実行して確認します。既存環境がmise管理なら、その実行経路に従います。Pythonが存在しないか必要なバージョンを満たさない場合だけ、既存のパッケージ管理方法で導入・更新します。最新版への追従は必須にせず、システムや他プロジェクトの既定値を変更しません。

使用するPythonの実行経路は `config.json`、確認時のバージョンと動作確認結果は `environment.md` に記録します。JevもPython標準ライブラリで動作します。任意の音声認識など別の依存が必要な機能は、そのセットアップで扱います。

| 状態 | 意味 |
|---|---|
| `ready` | 必要なツール・モデルがあり、選択機能の取得・変換を確認済み |
| `unverified` | バージョン確認まで、またはサンプルや通信の都合で実処理を確認できていない |
| `blocked` | 必要な言語データや認証がない、実行に失敗するなど、利用を妨げる条件がある |

選んだ機能がすべて `ready` になればセットアップ完了です。一部だけ使える場合は部分完了として、使える機能と残る条件を示します。再実行では、変更や不足に関係する項目だけを確認します。

## 3. 設定と調査資料の保存場所

| 保存先 | 内容 |
|---|---|
| `~/.config/digger/config.json` | 調査先、原本の保持方針、利用機能、言語・モデル、認証参照、Wiki連携 |
| `~/.local/state/digger/environment.md` | このマシンのツールの解決先・バージョン、確認日時、動作確認結果 |
| 選択した調査先の `<話題>/` | 原典の抽出本文、抜き書き、探索地図、探索ログ |
| 選択した別の原本ルートの `<話題>/` | 原本を別置きする場合のPDF・音声・動画 |

`XDG_CONFIG_HOME` と `XDG_STATE_HOME` に有効な絶対パスが設定されている環境では、それぞれを使います。利用設定はスキル本体の外に置くため、スキルを更新しても残ります。

別のマシンへ設定を持っていった場合は、保存先と認証参照を確認し、環境記録を作り直します。以前のマシンの確認結果だけで、ツールやモデルが使えるとは判断しません。

Obsidian の保存先は登録情報から解決します。以前の絶対パスや、そのとき開いている Vault に切り替えることはありません。選んだ Vault が見つからない場合は、その問題を解消してから保存します。

## 4. 調査の流れ

### 設定の読み込みと調査の再開

`digger` は利用設定と環境記録を読み、今回使う取得方法が実行できるか確認します。未設定なら `setup-digger` を案内します。不足があれば該当機能を修復するか、利用可能な資料だけで続けるかを確認します。

話題ごとに短い英小文字・ハイフンのディレクトリを作ります。同名の調査があれば内容を読み、同じ問いなら続きを行い、別の問いなら別名にします。再開時も、原典と過去の探索ログを保持します。

### 問いを分け、探索の入口を見つける

Obsidian連携を選んでいる場合は、外部調査の前に既存Wikiと出典を確認します。qmdを使える場合は既存の `vault-rag` のwiki-first手順を使い、使えない場合はWikiの索引とファイル検索から読む形にします。既知の内容と今回足りない内容を分け、同じ原典を取得済みなら本文・版・取得範囲を確認して再利用します。具体的な流れとJevを補助に使う手順は第7節に記載します。

最初に、答えるために確認したい論点を3〜6個作ります。最初の論点は「この分野の知見はどこに集まっているか」とし、依頼の具体的な条件を含む論点を少なくとも1つ入れます。半分以上は、効果・限界・失敗例など、本文を読む必要のある問いにします。

次に、日本語と英語、または用語検索と総説・入門資料のように、異なる2つの探し方を使います。用語、人物、知識が集まる場所、定番の資料を集めます。「見つけた」「探したが無い」「探していない」を区別し、未探索の手がかりを残します。この入口を探す段階が0周目です。

Codex では同じ実行者が2つの探し方を順に行います。並行エージェントを使う場合はユーザーの明示的な依頼に基づき、同時に2本までとします。

### 原典を取り込み、引用・リンク・著者をたどる

原典を取得し、必要な節が読めることを確認して保存します。ログイン画面や途中で切れた取得結果は、本文を保存できた資料として数えません。原典の題名・著者・公開日・URL・取得日時・抽出方法・取得範囲を記録します。

資料からは、参考文献や記事内リンクを後ろへたどる、引用した後続資料を探す、著者の別の発信を読む、同じ場や一覧を見る、増えた用語で検索し直す、といった方法で進みます。論文の索引に情報がなくても、本文の参考文献や著者自身の一覧を確認します。

原典を保存して、そこから少なくとも1回、引用・リンク・著者をたどるまでを1周とします。各論点に、根拠のファイル・行・ページ・時刻と短い原文を対応させ、検索語、取得失敗、次に進む理由をログへ追記します。

### 調査を終了する条件

ユーザーが指定した時間・回数の上限を優先します。通常は0周目の後に最低1周進め、次のいずれかで終了します。

ただし、開始前の既存資料の確認だけで今回の問いに答えられ、追加調査や最新情報の確認を求められていない場合は、外部探索を始めず既存の出典を案内できます。この場合は「既存資料で充足」と記録し、探索の飽和や新規調査の完了とは区別します。

| 終了理由 | 判定 |
|---|---|
| 根拠が揃った | 全論点に原文の位置が付き、限定条件も記録できた |
| 探索が飽和した | その周で挙がった人物・資料の7割以上が既知で、新しい用語もほとんど出ない |
| 周回上限に達した | 4周を終えた |
| 入手できる手がかりが尽きた | 残る根拠がログイン・有料の先にあり、正規の公開版も見つからない |
| 指定された上限に達した | ユーザーが定めた時間・回数に達した |

飽和は、同じ問いを異なる方法で探した結果で数えます。別仮説どうしの結果や、候補から関連資料を1本も取得できなかった周は、飽和の判断に使いません。ログに既知の件数と全件数を残します。

7割という値は imozuru の試行上の目安です。飽和や回数上限で止まった場合は、未解決の論点を明示します。無料ページが取得制限で読めない場合は、利用できるブラウザやユーザーによる閲覧も検討します。

## 5. 抜き書きと成果物

| ファイル | 役割 |
|---|---|
| `map.md` | 問い、論点、用語・人物・場、原典一覧、次の手がかり |
| `log.md` | 探索経過、取得失敗、判断理由、終了理由 |
| `sources/` | 本文、字幕、OCR・音声認識の出力、原典ごとのメタデータ |
| `extracts.json` | 原文と照合する抜き書きデータ |
| `report.md` | 調査の問い、出典位置付きの抜き書き、終了理由、未解決点を読む入口。Wikiへの入力もこのファイルに絞る |
| `report.html` | 標準でMarkdownと一緒に作る、前後の文脈を開ける抜き書きページ。ブラウザで読む入口 |

抜き書きは原文から切り出し、訳・注記と区別します。食い違う資料は原文を並べ、どちらを採るかの結論を付けません。OCRや自動字幕の誤変換も引用内で書き換えず、機械抽出であることを明記します。

探索地図の短い引用は原典を見つけ直す目印です。最後の抜き書きは段落・節を読み直し、主語、対象、理由、必要な手順、条件・例外が分かる範囲を選びます。人のやり方を調べる場合は人ごとに手順と理由をまとめ、作業順・信号順・説明順を区別します。外国語には訳を添えます。[作成基準と具体例](../digger/references/extracts.md)をスキルに同梱しています。

`report.py` は imozuru のコミット `ecb82c71b611872a0f49e783eda3bec987c80d91` から変更せず取り込んだものです。保存済み原文と `extracts.json` の抜き書きを照合し、HTMLを生成します。原典のダウンロードは担当しません。

照合は指定範囲の前後2行を含め、空白・箇条書きの印を正規化して行います。不一致があれば出典位置と原文を確認し、照合が通るまで新しい抜き書きページを作りません。照合と、有効な場合のJev確認を終えた同じデータから `report.md` と `report.html` を作ります。両方の生成成功を確認し、HTMLを読む入口、Markdownを保存・Wiki連携用として案内します。片方の失敗は部分完了として伝えます。ユーザーが形式を明示的に限定した場合だけ、その指定に従います。これは文字列の一致確認であり、引用が論点の根拠になるか、OCRや翻訳が正確かは別の確認です。

`report.md` は従来案の `extracts.md` を置き換えるもので、同内容のMarkdownを二重に生成しません。引用、訳、調査上の判断を分け、各引用から `sources/` の本文位置と原典URLへたどれるようにします。Markdown生成は digger 側の責務で、現在の `report.py` にこの機能はありません。

終了時は、抜き書きの保存場所、優先して読む原典2〜4本と読む箇所、確認できた範囲、未確認点、終了理由を返して完了します。満足度や感覚を尋ねる定型質問は付けません。ユーザーから調査範囲や深さへのフィードバックがあれば、そのままログへ残します。

## 6. ObsidianとWikiへの連携

Obsidian では既存の `obsidian-vault` の保存先解決・原文保護・リンク規約に従います。関連ノートへのリンクはメタデータや生成した説明へ付け、原文本文は保持します。同名のファイルを取り違えないよう、`[[digger-research/<話題>/report]]` のようにVault相対パスで参照します。

`obsidian-vault/references/save-destinations.md` を保存先規約の正本として、選択した digger のルートを登録しました。`vault-organization.md` にも、配下は生成・取得ツールが管理し、通常のノート整理で話題別の別フォルダへ移動しないことを記載しました。`sources/` の原文や探索ログを、自動リンク付けやWiki整理の編集対象にはしません。

Wikiへの反映方法はセットアップで選びます。初期提案の `manual` は調査資料の保存までで完了し、Wiki更新を別途呼び出します。`after-research` は調査終了後に設定したWikiスキルへ、今回の `<話題>/report.md` だけを入力として渡します。

`wiki-update` はファイルパスを明示した入力に対応しています。連携時には再登場確認に調査レポートだけを加え、同じ調査内の複数原典を「別の日に再登場した」と数えません。日付指定の自動取り込み範囲は広げず、diggerからの明示入力を使います。既存の出典リンク検証はVault相対パスを解決できるため、上記のパス付きリンクを使います。

`wiki-update` には入力資料の本文へリンクを付ける手順もあるため、diggerのレポートでは引用部分を編集しない規約を加えます。関連Wikiへのリンクは生成した説明・メタデータに限り、レポート再生成時にも保持します。Wikiの出典は `report.md` に置き、そこから元の引用・原典へ戻れる形にします。

現在の `wiki-update` は、今回の資料に加えて未処理台帳なども処理します。自動連携を選ぶときは、その通常の更新範囲も説明して確認します。対象Vaultや入力形式が合わない場合は連携を有効にしません。

### LLM Wikiの原典との整合

[KarpathyのLLM Wiki](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f) は、保持する原資料、更新されるWiki、運用規約を分ける構成です。diggerは原資料の収集と調査記録を担当し、知識の統合は既存のWikiで行います。qmdはその検索を助けます。

この設計で注意すべき点は、`report.md` を新しい一次資料と誤認することです。レポートは選択された引用と判断の派生物なので、Wiki更新時の入口をレポートに絞っても、根拠確認のために元資料へ降りることは制限しません。Wikiがレポートの要約だけを再要約し続ける構造にはしません。

既存の `wiki-update` には、原典との違いとして次の運用規則があります。今回は既存ルールを変更せず、連携上の判断材料として残します。

| 確認した規則 | 原典と比べた位置づけ・影響 |
|---|---|
| 別の日に再登場するまで新規ページ化を保留 | 個人Vault固有の整理方針。単発でも深く調べた話題がWikiにならないことがある。レポートは残し、調査しただけで例外扱いにしない |
| ソース本文へのwikilink追加 | 原資料を不変に保つ方針と緊張がある。diggerの原典と引用は対象外とし、生成説明・メタデータだけに付ける |
| 1回の取り込みで10〜15ページの更新を想定 | 原典では運用の一例。ページ数を達成目標にせず、新しい根拠がある既存ページを更新する |

## 7. Jevによる不足判定と文脈確認

### 既存知識から不足を探す

外部から集めた後の確認に加えて、`qmd → 既存資料の読解 → Jevによる不足の判定 → digger` という入口を任意で利用できます。Jevは任意の補助であり、qmdで候補を探して本文を読む段階は、Jevなしでも行えます。

1. 今回の問いでWikiを検索し、関連ページを読みます。既存の `vault-rag` と同じく、スニペットだけでは判断せず、必要な箇所は出典まで確認します。
2. 各論点について、既存の根拠、適用条件、日付、食い違い、未確認点を整理します。Jevを使う場合は、この資料と論点を渡して不足や矛盾の候補を判定させます。
3. 足りる論点は出典を案内し、足りない論点をdiggerの探索へ渡します。更新確認が必要なものは「不足」と区別して調べます。検索で見つからないだけの場合は、索引の鮮度と既知のファイルも確認します。
4. 外部で得た原典から照合済みのレポートを作り、選択した連携方法で既存Wikiを更新します。Wikiから生まれた問いを元のページへつなぎ直します。

例えばWikiに「低遅延の音声合成方式」はあるが「日本語での測定条件」がない場合、既存の方式一覧を読み直したうえで、不足する測定条件を外部調査の論点にします。取得済みの資料はURLやDOI、版と本文を確認して再利用し、Wikiとその出典レポートを独立した二つの裏付けとして数えません。

qmdの順位やJevのconfidenceだけでは、十分な根拠があるとは判定しません。Jevに送る既存資料もセットアップで合意した送信範囲に含めます。未設定なら読解による確認を行い、Jevへ自動送信しません。

qmd連携を選ぶ場合は、セットアップで対象collectionとVaultの対応を確認します。既存の `vault-rag` はVault内のMarkdownを広く検索する設計なので、新しいルートを置くだけでも探索ログ等が候補に入る可能性があります。初期の検索対象はWikiと調査レポートを中心にし、原典は出典リンクから読む構成を提案します。索引設定を変える場合は、既存の検索品質測定を使って影響を確認します。

### 取得後の引用を確認する

取得後は `scripts/jev.py citations` で、原典の裏付け、表示する引用の十分さ、同じ節の引用全体による論点の充足を別々に確認します。原典の周辺に説明があっても表示する引用から抜けていれば修正対象です。注記と既存のstatusは判定材料に含めません。TypeSafe の[引用チェック例](https://docs.typesafe.ai/cookbooks/citation_check)にも、文字列照合後に意味の関係を判定する手順があります。

原典にある説明の抜き漏れは引用を修正し、原典自体に説明がない場合だけ追加探索へ戻ります。条件が違う事例は分け、実演の未確認はそのまま残します。「付いた」は引用全体で論点に答える場合とし、必要な部分が残るなら「一部だけ」にします。Jevの指摘は実行者が原文で確かめ、引用文を自動補作したりconfidenceだけで完了を決めたりしません。

例えば、原文が「ある条件では改善したが、別の条件では効果がなかった」と述べている場合、前半だけの引用でも文字列照合は通ります。Jev には論点と周辺の段落を渡し、後半の条件も必要か、引用が問いに答えているかを判断させます。

| 導入段階 | Jevの役割 | 終了条件への影響 |
|---|---|---|
| 今回の実装 | 抜き書きが根拠になっているか、条件・否定を落としていないかを確認 | 元版の終了条件を維持 |
| 将来の結果比較 | 各周の根拠不足や新しい知見の有無を判定し、結果を記録 | 判断を記録して比較し、終了は従来どおり |
| 将来、有効性を確認した後 | 不足した論点を次の探索へ回す判断に利用 | 実データで評価したうえで変更を検討 |

抜き書きの候補を選ばせる場合も、文は選択された原文の範囲から取り出します。Jevの判定は原文と別に残し、食い違う資料を消したり、原文を書き換えたりする理由にはしません。

Choice・Scoreの confidence は回答分布の集中度で、調査の網羅率を示す値ではありません。高い値だけを理由に調査を終える設計にはしません。[confidence の仕様](https://docs.typesafe.ai/confidence)

セットアップで利用有無、モデル、認証参照、送信する資料のディレクトリ、topicごとの呼び出し回数、1回の送信量を決めます。初期提案は8回・60,000バイトです。全結果を実行者が原典と照合し、API失敗・上限到達時は未確認として通常の読解へ戻します。自動再試行はしません。原文やreport.pyは変更せず、判定は `topic/jev/result-*.json` に別保存します。入力形式・コマンド・設定は [Jev連携](../digger/references/jev.md) を参照してください。

| `fetch.py`・`chain.py`・`watch.py` | 取り込み済み。手動User-Agent指定を除去し、元版の転送・サイズ検査を維持。直接通信が使えない環境はWeb/axを利用 |
| インストールと初回セットアップ | 未実施。利用者の保存先やモデルなどの値はまだ設定していない |

Pythonの選択、専用の `digger-research/`、`report.md` とWiki規約への接続をスキルへ反映しました。ユーザー環境の設定ファイル、Vault、qmd索引は変更していません。

### 元版の取得・探索スクリプトの扱い

`fetch.py`・`chain.py`・`watch.py` の3つも取り込みました。Web検索やaxだけで役割をすべて置き換えられるものではないため、元版の振る舞いを残す方針に合わせ、次の役割を引き継ぎます。

| 元版のスクリプト | 確認できた役割 | diggerでの扱い |
|---|---|---|
| `fetch.py` | PDF抽出・OCR、原言語の字幕選択、HTML抽出、取得範囲・不完全取得の検出 | 選んだ機能について処理を引き継ぐ。Webの探索・取得には利用可能なWeb機能またはaxを使い、抽出品質の確認を残す |
| `chain.py` | OpenAlexによる参考文献・被引用・著者の探索 | 論文をたどる補助手段として残す。サービスの利用条件と接続をセットアップで確認する |
| `watch.py` | RSS/Atomの登録、新着確認、既読状態の保持 | 継続調査を選ぶ場合の任意機能として残す。定期実行は別途指定がある場合だけ設定する |

元版の `fetch.py` もHTML抽出にaxを使っています。URLを独自に取得してからローカルHTMLをaxへ渡す構成で、axはPDF・OCR・字幕処理や取得失敗の判定全体の代替ではありません。diggerではaxによるページ探索を活用しつつ、その後の保存・品質確認を分けて扱います。

取得補助のHTTP処理は、リダイレクト先・取得サイズ・部分取得の検査を残しました。手動User-Agent指定と、それによるPDFの取り直しは除去しました。この環境のように取得方法をWeb/axへ指定している場合は、補助の直接通信を実行せず、Web/axで取得してローカル変換します。`fetch.py` はOCRの明示選択と原字幕の保持にも対応しました。変更せず取り込んでいるのは `report.py` だけです。

Jev連携の実装は追加済みです。利用者の初回セットアップと、実資料での精度評価は別の作業として残っています。
